# 작업 예제: 자동완성 검색창 (클라이언트 주도 요청 응답형)

Input과 Dropdown 두 조각으로 보이는 UI가 실제로는 디바운싱과 캐싱, 경쟁 조건, 접근성이 전부 걸린 문제다. 클라이언트가 묻고 서버가 답하는 형태의 기능을 설계할 때 이 예제의 결정 과정을 따라가면 같은 질문들을 만나게 된다.

## R. 무엇을 보장할 것인가

기능 요구사항부터 적는다.

- 입력하면 추천어 목록이 뜬다
- 키보드 위아래로 항목을 오간다
- Enter로 검색하고 Escape로 닫는다
- 두세 글자 미만의 짧은 입력에는 결과를 띄우지 않는다

기능만으로는 설계가 서지 않는다. 보장으로 바꾼다.

- 입력을 멈춘 뒤 결과가 보일 때까지 p75 기준 500ms 이하
- 타이핑마다 서버를 때리지 않는다
- 느린 네트워크에서 이전 입력의 결과가 나중에 도착해도 화면을 덮지 않는다
- 키보드와 스크린리더만으로 전 기능을 쓸 수 있다
- 추천 API가 죽어도 검색 자체는 된다

이 단계에서 설계를 가르는 질문이 나온다. 개인화를 하는가(캐시 키가 달라진다), 추천어 랭킹은 서버 몫인가(클라이언트는 받은 순서를 유지만 하는가), 최소 입력 길이는 몇 글자인가. 각 답이 그대로 아래 단계의 결정이 된다.

## A. 상태의 원천과 데이터 흐름

먼저 통신 성질. 타이핑마다 반응하니 실시간처럼 보이지만 주도권은 클라이언트에 있다. 클라이언트가 묻고 서버가 답하는 단방향 요청 응답이라 HTTP가 맞다. 무상태라서 수평 확장과 CDN 캐싱이 따라오고 취소도 AbortController로 표준적이다. "실시간이니 WebSocket"이라는 통념을 성질 분석이 뒤집는 사례다.

요청 밀도는 디바운스로 줄인다. 입력이 멈춘 뒤 200ms에서 300ms를 기다렸다 요청한다. 서버 부하와 체감 반응성 사이의 균형점이고, 정확한 값은 운영에서 조정한다.

입력에서 화면까지의 경로를 컨트롤러 하나로 모은다. 캐시 확인, 디바운스, 이전 요청 취소, 요청, 응답 검증, 상태 갱신이 전부 같은 길을 지난다. 모든 경로가 한 곳을 지나야 경쟁 조건의 해결점이 한 곳에 모인다.

상태 분류는 이렇다.

| 상태                                   | 분류          |
| -------------------------------------- | ------------- |
| inputValue, isOpen, highlightedIndex   | Local UI      |
| results, isLoading, error              | Server (캐시 대상) |
| canShowDropdown                        | Derived       |
| 검색 결과 페이지로 넘어갈 때의 검색어  | URL           |

## D. 화면을 위한 모델

API는 하나다.

```
GET /api/autocomplete?q=java&limit=10
응답: { query: string, results: Result[] }
```

응답에 query를 에코해 담는 것이 이 설계에서 가장 중요한 결정이다. 응답이 도착한 시점의 입력값과 응답의 query가 다르면 그 응답은 버린다.

경쟁 조건 방어는 이중이다.

1. 새 요청을 보내기 전에 이전 요청을 AbortController로 취소한다
2. 그래도 도착한 응답은 `response.query === 현재 입력값` 검증으로 거른다

취소가 첫 번째 방어선이고 에코 검증이 두 번째다. 사용자가 java까지 치고 javascript로 이어 쳤는데 느린 네트워크에서 java의 응답이 나중에 도착하는 장면을 생각하면 두 겹이 왜 필요한지 보인다. 취소는 아직 안 떠난 요청만 막고, 이미 떠난 요청의 늦은 응답은 검증만이 막는다.

같은 쿼리의 중복 요청은 캐시로 없앤다. Map 기반 인메모리에 TTL을 붙인 정도면 충분하다. 개인화가 있다면 캐시 키에 사용자 차원이 들어가야 한다는 것을 R에서 정한 답이 알려준다.

## I. 경계의 계약

컴포넌트는 책임으로 나눈다.

```
Autocomplete (상태 조립)
├─ SearchInput (입력, 포커스, 키보드)
└─ ResultDropdown (목록과 로딩, 에러, 빈 값 상태)
   └─ ResultItem (개별 항목)
```

핵심 구현은 useAutocomplete 훅에 모은다. 반환은 query와 setQuery, results, isLoading, isError, isOpen, handleKeyDown이다. 컴포넌트는 이 반환만 알고 디바운스와 캐시, 취소는 훅 안에 감춘다.

접근성은 WAI-ARIA combobox 패턴이 계약이다.

| 자리       | 계약                                                             |
| ---------- | ---------------------------------------------------------------- |
| input      | role="combobox", aria-expanded, aria-controls, aria-autocomplete="list" |
| 드롭다운   | role="listbox", 각 항목은 role="option"                          |
| 포커스     | DOM 포커스는 input에 유지, 활성 항목은 aria-activedescendant로 전달 |
| 키보드     | 위아래로 이동, Enter 선택, Escape 닫기, Tab은 자연 포커스 이동   |

포커스를 input에 유지하는 것이 이 패턴의 요점이다. 포커스가 목록으로 넘어가면 타이핑을 이어갈 수 없다.

텔레메트리 스키마도 여기서 정한다. 요청 지연, 에러율, 캐시 히트율, stale 응답 폐기율을 남긴다.

## O. 검산과 운영

디바운스와 캐시, 취소, 에코 검증은 이미 앞에서 정해졌다. 이 단계는 나머지를 다듬는다.

**장애.** 2초에서 3초의 타임아웃을 두고 넘으면 실패 처리한다. 추천은 enhancement라 조용히 접고, 검색 기능은 유지한다. 정책에 따라 안내를 띄우거나 캐시된 인기 검색어로 대신한다.

**지표.** 체감 지표는 입력 멈춤부터 추천어 노출까지의 시간이다. 시스템 지표는 api_latency_ms, api_error_rate, cache_hit_rate, stale_response_discard_rate다.

지표는 교차로 읽어야 원인이 나온다. stale 폐기율이 높은데 api 지연이 정상이면 서버 문제가 아니라 디바운스가 짧은 것이다. 폐기율과 지연이 같이 높으면 서버 쪽이다.

**운영.** 디바운스 값은 A/B로 조정한다. 봇과 남용은 rate limit으로 막는다. 배포는 feature flag로 점진한다.

## 이 예제가 보여주는 것

주도권이 클라이언트에 있다는 R의 한 문장이 HTTP 선택과 디바운스, 에코 검증, 조용한 폴백까지 전부 결정했다. 서버가 먼저 말을 거는 기능이었다면 같은 질문에서 전혀 다른 답이 나온다. 그 경우는 case-realtime.md의 채팅 예제가 보여준다.
