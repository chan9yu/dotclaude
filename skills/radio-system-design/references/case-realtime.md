# 작업 예제: 실시간 채팅 (서버 주도 실시간형)

채팅이 자동완성과 근본적으로 다른 이유는 한 문장이다. 서버가 먼저 말을 건다. 클라이언트가 묻지 않았는데 상대의 메시지가 도착해야 하고, 이 사실이 통신과 상태, 데이터 모델, 인터페이스를 전부 갈라 놓는다. 서버가 먼저 밀어주는 기능을 설계할 때 이 예제의 결정 과정을 따라간다.

## R. 무엇을 보장할 것인가

기능은 메시지 전송과 실시간 수신, 전송 상태 표시(전송 중, 전송됨, 실패), 과거 메시지 로드, 읽음과 타이핑 표시다.

보장은 셋이다. 잃지 않고, 즉시 반응하고, 순서대로.

- 전송 버튼을 누르면 서버 응답을 기다리지 않고 즉시 화면에 보인다
- 네트워크가 끊겨도 보내려던 메시지를 잃지 않는다
- 메시지 순서가 모든 참여자에게 같다
- 같은 메시지가 두 번 뜨지 않는다
- 수천 개 메시지가 쌓여도 스크롤이 버벅이지 않는다

설계를 가르는 질문 둘이 이 단계에서 나온다.

**전송 버튼을 누르면 언제 화면에 보여주나.** 서버 응답을 기다리면 지연 동안 사용자가 재전송을 시도한다. 즉시 표시(낙관적 처리)가 필수이고 이 답이 데이터 모델 전체를 결정한다.

**순서는 누가 정하나.** 기기 시계는 어긋난다. 클라이언트 시각이 아니라 서버의 순번이 기준이어야 한다.

체감 속도는 셋으로 갈라 잰다. 내 말풍선이 뜰 때까지(낙관적 처리 덕에 네트워크와 무관하게 0에 수렴해야 한다), 상대 메시지가 도착할 때까지(서버와 네트워크에 의존한다), 방에 들어가 첫 메시지가 보일 때까지(진입 체감이다). 하나로 뭉치면 어디가 느린지 알 수 없다.

## A. 상태의 원천과 데이터 흐름

서버가 먼저 말을 걸어야 하니 지속 연결이다. 방식을 비교하면 이렇다.

| 방식         | 성질                  | 판정                          |
| ------------ | --------------------- | ----------------------------- |
| Polling      | 주기적으로 물어봄     | 지연과 낭비가 커서 부적합     |
| Long Polling | 응답을 붙잡아 둠      | 과도기 기술                   |
| SSE          | 서버에서 클라 단방향  | 수신만 필요하면 가능          |
| WebSocket    | 양방향 지속 연결      | 송수신이 다 필요해 여기에 맞음 |

고정하는 것은 프로토콜이 아니라 지속 연결이라는 성질이다. 전송 계층을 추상화해 두면 MQTT나 WebRTC DataChannel로도 갈아 끼울 수 있다.

데이터 흐름에서 가장 중요한 지점은 송신 경로(내가 보낸 낙관적 메시지)와 수신 경로(서버가 내려준 확정 메시지)가 만나는 곳이다. 여기서 병합이 새면 말풍선이 두 개 뜬다.

연결은 boolean이 아니라 생명주기다. 끊김, 재연결, 인증, 누락 동기화, 준비됨을 거친다. 재연결 설계는 세 조각이다.

- 못 보낸 메시지는 전송 큐(outbox)에 쌓았다가 재전송한다
- 못 받은 메시지는 마지막으로 받은 순번 이후를 동기화한다. 커서가 서버 보관 범위를 벗어났으면 스냅샷으로 교체한다
- 재접속 시점은 백오프로 늦춘다. 즉각 재접속은 재연결 폭풍을 만든다

## D. 화면을 위한 모델

메시지에 식별자가 둘 필요하다.

```typescript
type Message = {
	clientMessageId: string; // 클라가 즉시 발급(UUID). 낙관적 표시와 중복 제거의 키
	serverSeq: number | null; // 방 단위 단조 증가 순번. 모든 정렬의 기준. 확정 전 null
	senderId: string;
	body: MessageBody;
	status: 'sending' | 'sent' | 'failed';
	createdAt: string; // 표시 전용
};
```

낙관적 병합 흐름은 여섯 걸음이다.

1. 전송 버튼을 누른다
2. clientMessageId를 발급하고 sending 상태로 즉시 화면에 그린다
3. 지속 연결로 전송한다
4. 서버가 serverSeq를 붙여 확인(ack)을 내려준다
5. clientMessageId로 기존 항목을 찾아 갱신한다. 새로 추가하면 두 개가 뜬다
6. 상태를 sent로 바꾼다

순서와 중복, 누락은 serverSeq 하나의 규칙으로 처리한다. 받은 순번이 마지막과 같으면 중복이니 무시하고, 바로 다음이면 처리하고, 갭이면 그 구간의 동기화를 요청한다. 재연결 복구는 이 갭 동기화의 극단적 사례일 뿐이다.

읽음 표시는 규모와 무관하게 만든다. 누가 읽었는지 목록을 내리면 단체방에서 페이로드가 인원에 비례해 는다. 내리는 쪽은 unreadCount 하나, 올리는 쪽은 이 방의 마지막 읽은 순번 하나면 트래픽이 메시지 수와 무관해진다.

## I. 경계의 계약

UI가 WebSocket을 직접 만지면 재연결과 큐, 순서 로직이 컴포넌트마다 흩어진다. 엔진 하나로 모은다.

```typescript
interface ChatEngine {
	connect(roomId: string): Promise<void>;
	send(body: MessageBody): ClientMessageId; // 낙관적 식별자를 즉시 반환한다
	subscribe(event: ChatEvent, listener: Listener): Unsubscribe;
	loadBefore(seq: number): Promise<Message[]>;
	disconnect(): void;
}

type ChatEvent = 'message' | 'ack' | 'receipt' | 'typing' | 'connection';
```

send가 서버 응답이 아니라 식별자를 즉시 반환하는 것이 낙관적 UI의 계약이다.

엔진 아래에 전송 계층을 한 겹 둔다.

| 계층                                    | 아는 것               |
| --------------------------------------- | --------------------- |
| UI 컴포넌트                             | ChatEngine            |
| ChatEngine (큐, 순서, 중복 제거)        | 전송 계층의 추상 계약 |
| WebSocket, SSE, MQTT, DataChannel 구현  | 실제 프로토콜         |

새 프로토콜 도입은 전송 구현 하나를 추가하는 일이 되고 엔진과 UI는 그대로다.

이벤트는 공통 봉투 `{ roomId, seq, type, payload }`로 통일한다. 종류가 늘어도 정렬과 중복 제거는 바깥 필드만 보고 같은 규칙으로 돈다.

접근성 계약: 새 메시지 도착은 aria-live="polite"로 알리고, 타이핑 표시처럼 자주 바뀌는 정보는 지나치게 자주 읽히지 않게 조절한다. 목록은 논리적 순서를 유지하고 키보드로 탐색할 수 있어야 한다.

## O. 검산과 운영

**가변 높이 가상화.** 채팅 목록은 일반 목록보다 어렵다. 항목 높이가 제각각이고(한 줄 텍스트와 이미지, 파일이 섞인다) 위로도 자란다(과거 로드). 렌더 후 높이를 측정해 캐시하고, 과거 메시지를 위에 붙일 때는 스크롤 위치를 보정(anchoring)하고, 새 메시지 도착 시 자동 스크롤은 사용자가 바닥에 있을 때만 한다.

**오프라인.** 못 보낸 것은 outbox에 담아 로컬 저장소(IndexedDB)에 두고 sending 상태로 표시한다. 재연결 후 순서대로 재전송하면 중복은 순번 규칙이 걸러 준다. 못 받은 것은 커서 이후 동기화다. 좀비 연결은 주기적 ping과 pong으로 걸러 몇 번 무응답이면 끊긴 것으로 본다.

**재접속 폭풍.** 수만 명이 동시에 끊기는 장면을 전제한다.

```typescript
const maxDelay = Math.min(CAP_MS, BASE_MS * 2 ** retryCount);
const delay = Math.random() * maxDelay; // full jitter
```

지수 백오프만으로는 부족하다. 모두가 같은 시각에 재시도하면 복구 중인 서버가 다시 무너진다. jitter가 재시도를 구간 안에 흩는다. 서버가 내려준 재시도 시점(retryAfter)이 있으면 우선하고, 자동 재시도는 네트워크 오류에만 하고, 연결이 안정되면 retryCount를 초기화한다.

**유입 제어.** 이벤트가 처리 속도를 넘게 쏟아지면 프레임 단위로 모아 한 번에 반영한다. 타이핑 표시는 최신만 남기고 메시지는 동기화 큐로 처리한다. 이벤트마다 등급이 다르다.

**지표.**

| 층          | 지표                                                                     |
| ----------- | ------------------------------------------------------------------------ |
| 체감        | send_to_echo_ms, delivery_latency_ms, time_to_first_message_ms, time_to_chat_ready_ms |
| 시스템      | ws_reconnect_rate, message_send_failure_rate, duplicate_message_rate, out_of_order_rate, session_resume_success_rate |

duplicate_message_rate는 0이어야 정상이다. 0이 아니면 낙관적 병합 설계가 샌 것이니 D 단계로 돌아간다. 이렇게 0이어야 하는 지표가 설계의 검산 장치가 된다.

**운영.** 스팸은 rate limit으로 막고, 사용자 입력을 렌더링하니 sanitization이 필수이고, 탭이 여럿이면 SharedWorker로 연결을 공유하는 안이 있지만 복잡도 대비 효과를 실측한 뒤 도입한다. 백오프 값 같은 파라미터는 실사용 데이터로 조정한다.

## 이 예제가 보여주는 것

서버가 먼저 말을 건다는 R의 한 문장이 지속 연결과 낙관적 병합, 식별자 이원화, 재전송 큐, jitter 백오프까지 전부 결정했다. 클라이언트가 묻는 기능이었다면 같은 질문에서 전혀 다른 답이 나온다. 그 경우는 case-request-response.md의 자동완성 예제가 보여준다.
